Data Flow Diagram  
 
The following discussions are based from Tutorials Point (I) Pvt. Ltd.  
(2014). Data Flow Diagram (DFD) is a graphical representation of flow of data 
in an information system. It is capable of depicting incoming data flow, 
outgoing data flow, and stored data. The DFD does not mention anything 
about how data flows through the system.  
 
There is a prominent difference between DFD and Flowchart. The 
flowchart depicts flow of control in program modules. DFDs depict flow of 
data in the system at various levels. It does not contain any control or branch 
elements.  
 
Types of DFD  
 
Data Flow Diagrams are either Logical or Physical.  
 
• Logical DFD - This type of DFD concentrates on the system process, and 
flow of data in the system. For example, in a banking software system, 
how data is moved between different entities.  
• Physical DFD - This type of DFD shows how the data flow is actually 
implemented in the system. It is more specific and closer to the 
implementation.  
 
DFD Components  
 
DFD can represent source, destination, storage, and flow of data using 
the following set of components 
 
 
The DFD Components 
 
 
• Entities - Entities are sources and destinations of information data. 
Entities are represented by rectangles with their respective names.

HIPO Diagram  
 
The following discussions are based from Tutorials Point (I) Pvt. Ltd.  
(2014). Hierarchical Input Process Output (HIPO) diagram is a combination of 
two organized methods to analyze the system and provide the means of 
documentation. HIPO model was developed by IBM in year 1970.  
 
HIPO diagram represents the hierarchy of modules in the  software 
system. Analyst uses HIPO diagram in order to obtain high-level view of system 
functions. It  decomposes functions into sub -functions in a hierarchical 
manner. It depicts the functions performed by system.  
 
HIPO diagrams are good for documentatio n purpose. Their graphical 
representation makes it easier for designers and managers to get the pictorial 
idea of the system structure. 
 
A sample HIPO Diagram 
 
In contrast to Input Process Output (IPO) diagram, which depicts the 
flow of control and data in a module, HIPO does not provide any information 
about data flow or control flow.

Decision Tables  
 
The following discussions are based from Tutorials Point (I) Pvt. Ltd.  
(2014). A decision table represents conditions and the respective actions to 
be taken to address them, in a structured tabular format. It is a powerful tool 
to debug and prevent errors. It helps group similar information into a single 
table and then by combining tables it delivers easy and convenient decision-
making.  
 
Creating Decision Table  
 
To create the decision table, the developer must follow basic four 
steps:  
• Identify all possible conditions to be addressed  
• Determine actions for all identified conditions  
• Create Maximum possible rules  
• Define action for each rule  
 
 
Decision Tables should be verified by end -users and can lately be 
simplified by eliminating duplicate rules and actions.  
 
Example  
 
Let us take a simple example of day -to-day problem with our Internet 
connectivity. We begin by identifying all problems that can arise while starting 
the internet and their respective possible solutions.  
 
We list all possible problems under column conditi ons and the 
prospective actions under column Actions.

Data Dictionary  
 
The following discussions are based from Tutorials Point (I) Pvt. Ltd.  
(2014). Data dictionary is the centralized collection of information about data. 
It stores meaning and origin of data, its relationship with other data, data 
format for usage, etc. Data dictionary has rigorous definitions of all names in 
order to facilitate user and software designers.  
 
Data dictionary is often referenced as meta -data (data about data) 
repository. It is created along with DFD (Data Flow Diagram) model of 
software program and is expected to be updated whenever DFD is changed 
or updated.  
 
Requirement of Data Dictionary  
 
The data is referenced via data dictionary while designing and 
implementing software. Data dictionary removes any chances of ambiguity. 
It helps keeping work of programmers and designers synchronized while using 
same object reference everywhere in the program.  
Data dictionary provides a way of documentation for the complete 
database system in one place. Validation of DFD is carried out using data 
dictionary.

Data dictionary should contain information about the following:  
• Data Flow  
• Data Structure

Software Design Strategies 
 
When it comes to the process of creating and developing software, software 
engineers adhere to a set of standards and principles that are referred to as 
software design strategies. These methods are utilized to guarantee that software 
is developed in a method that is well -organized, productive, and successful, and 
that it satisfies the requirements of the end-users. 
 
In this unit, you will be learning the different design strategies that as future software 
developer must observe.   
 
Software Design Strategies 
 
Software design strategies are a collection of best practices, fundamental ideas, 
and guiding principles that are utilized by software engineers in the process of 
developing high-quality software systems. There are many different approaches to 
the design of software, such as: 
 
 Object-oriented design is a way of making software that focuses on using 
objects to represent real-world things and how they work together. Here's an 
example of a design based on objects: 
 
 Imagine that you are making a program for a library. In object -oriented 
design, you would make objects to reflect things like books, library patrons, 
and library staff. Each object would have attributes (data) and methods
--- page 2 ---
2 
 
(functions) that reflect the real -world entity it stands for in terms of its 
properties and actions. 
 
 The Book object , for example, would have properties like title, author, and 
ISBN, as well as methods like borrow() and return(). The Patron object would 
have properties and functions like name, ID, requestBook(), and 
returnBook(). The LibraryStaff object would have things like name and ID as 
properties and checkInBook() and checkOutBook() as methods. 
 
These items would talk to each other to show how things work in a real library, like 
checking out and returning books. For instance, when a Patron checks out a book, 
the borrow() method of the Book object is called, and the book's availability state is 
changed. The due date of the book would also be added to the Patron object. 
 
Object-oriented design helps make software that is modular, adjustable, and can 
be used over and over again. By dividing software into objects, we can make code 
that is easier to manage and add to over time. 
 
 Service-Oriented Architecture (SOA) creates a network of distributed 
services that connect to provide end -user functionality. Service -Oriented 
Architecture: 
 
 Let's you will develop an e -commerce web app. Services for the shopping 
cart, order processing, and payment processing would be created in a 
Service-Oriented Architecture. 
 
Each service would have a well-defined interface for interacting with other services. 
The shopping cart service may expose addItem() and removeItem(), whereas the 
payment processing service may expose authorizePayment() and 
capturePayment(). 
 
These services would communicate with each other using standardized protocols 
such as SOAP or REST. For example, when a user adds an item to their shopping 
cart, the shopping cart service would send a message to the order processing 
service to create a new order, and then the payment processing service would be 
called to authorize the payment. 
 
Service-Oriented Architecture creates flexible, scalable software. We can readily 
adjust systems to changing business needs and handle high traffic by separating 
the software into smaller, independently deployable services. 
 
 The Model -View-Controller (MVC) software design pattern divides an 
application into three interconnected parts: the model, view, and controller. 
Model-View-Controller example:
--- page 3 ---
3 
 
 Let's say you are designing a web application that displays a list of products 
and allows users to add products to their cart. In the MVC pattern, you would 
create a model that represents the data (the products and the cart), a view 
that displays the data to the user, and a controller that handles user input 
and updates the model and view accordingly. 
 
The model would include product data, cart data, and cart add/remove methods. 
The user would see the cart and product list. The controller would change the model 
and view based on user input like adding a product to the cart. 
 
When a user clicks "Add to Cart"  for a product, the controller calls the model's 
addProduct() method to update the cart data and then updates the view. 
 
MVC helps build modular, manageable, and scalable software. By dividing the 
program into three components, we may alter one without aff ecting the others and 
reuse components in other projects. 
 
 Agile software development stresses flexibility, cooperation, and quick 
iteration. Agile design: 
 
 Let's say you are designing a mobile app that allows users to track their 
fitness goals. In an Agile design approach, you would work in short iterations, 
called sprints, and prioritize features based on their value to the user. 
 
You work on a few things per sprint and collaborate with the development team and 
product owner to address user needs. We also reviewed and adjusted our progress 
often. 
 
In the first sprint, you might create a fitness goal -setting and progress -tracking 
interface. We may include a social component in the second sprint. 
 
Agile design creates user -responsive software. Working in short iterations and 
focusing user value helps us find and fix issues and deliver product that fulfills user 
demands rapidly. 
 
Software Design Approaches  
 
Software design techniques are the different ways that developers can make 
software systems that work well. Here are some different ways to create software: 
 
 Top-Down Design: Top-down design is a way of making software that starts 
with a big picture view of the system and then breaks it down into smaller, 
more doable parts. This method is often used in structured programming, 
and it can help make sure that the software system is well -organized and 
easy to manage (Dijkstra, 1968).
--- page 4 ---
4 
 
 Bottom-Up Design: Bottom-up design is a way of making software that starts 
with the parts of the system and then puts them to gether to make a whole 
system. This method is often used in object -oriented programming, and it 
can help make sure that the software system is simple and flexible (Johnson 
& Foote, 1988). 
 
 Component-based design is a way of making software that focuses on 
making flexible, reusable parts that can be put together to make a bigger 
software system. This method is often used in software engineering, and it 
can help make sure that the software system is scalable and flexible 
(Szyperski, 1999). 
 
 Domain-Driven Design: Domain-driven design is a way of making software 
that focuses on getting both the software writers and the domain experts to 
agree on how the domain works and what it needs. This method is often 
used when making enterprise software, and it can help make sure the system 
meets the wants of the end users (Evans, 2003). 
 
In conclusion, software design methods are very important for making good 
software systems. Some of the most popular ways to design software are top-down 
design, bottom-up design, component-based design, and domain-driven design. By 
using these methods, software writers can make software that is well -organized, 
modular, reusable, and meets the needs of end users.

User Interface Design 
 
User Interface Design (UID) is the process of developing user interfaces for digital 
systems such as websites, apps, and other software. It entails a number of activities 
aimed at creating intuitive and user -friendly interfaces that meet user needs and 
improve user experience (UX) (Dix et al., 2004). 
 
Some of the primary actions involved in User Interface Design are as follows: 
 
 
 User Research: Understanding user needs and requirements, as well as 
their behavior when dealing with digital systems, is part of this  activity. 
Surveys, interviews, observations, and other approaches can be used to do 
this (Rubin and Chisnell, 2008). 
 
 User Analysis is the process of evaluating user data in order to uncover 
trends, preferences, and behaviors. This assists designers in de veloping 
user personas that represent their target audience and serve as a guide for 
the design process (Cooper, Reimann, and Cronin, n.d). 
 
 Task analysis entails breaking down complex jobs into smaller, more 
manageable ones. This assists designers in iden tifying the stages users 
must take to complete a task and designing interfaces to support these steps 
(Preece, Rogers, and Sharp, 2015). 
 
 Information Architecture is the process of organizing information in a logical 
and ordered manner. This allows users t o discover information quickly and 
simply, as well as traverse the interface (Morville andRosenfeld, n.d.). 
 
 Wireframing is the process of producing low-fidelity sketches of the interface 
layout and design. This allows designers to visualize the interface structure
--- page 7 ---
7 
 
and test several design concepts before committing to a final design (Tidwell, 
2010). 
 
 Prototyping is the process of producing interactive, high-fidelity models of an 
interface design. This allows designers to test the interface with consumers 
and identify any usability concerns before developing the final product 
(Snyder, 2003). 
 
 User Testing: This activity entails putting the interface through its paces with 
real users in order to assess its usability and effectiveness. This can be 
accomplished through a variety of approaches, including usability testing, 
A/B testing, and user feedback (Sauro and Lewis, 2016). 
 
Finally, user interface design entails a number of actions aimed at creating intuitive 
and user-friendly interfaces. These actions assist designers in understanding user 
needs and behavior, designing interfaces that aid in user tasks, and testing  the 
interface with users to guarantee usability and effectiveness.

The following are some of the user interface golden rules: 
 
1. Strive for consistency: Users should not have to wonder whether different 
words, situations, or actions mean the same thing. A consistent interface is 
easier to use and learn (Shneiderman, 1998). 
 
2. Keep it simple: The interface should be simple and easy to use. The design 
should not be more complex than necessary (Nielsen, 1993). 
 
3. Provide clear and concise feedback: Users should be able to understand the 
system’s state and what to expect next. Feedback should be provided in a 
timely manner (Shneiderman, 1998). 
 
4. Use appropriate language and terminology: The langua ge and terminology 
used in the interface should be appropriate for the users’ level of 
understanding. Use language and terminology that users are familiar with 
(Nielsen, 1993). 
 
5. Minimize user memory load: Users should not be required to remember 
information from one part of the interface to another. The system should help 
users keep track of their location and provide clear navigation options 
(Shneiderman, 1998). 
 
6. Make it easy to recover from errors: Users should be able to recover from 
errors easily and with minimal loss of data. The interface should be designed 
in such a way that it prevents errors from occurring in the first place (Nielsen, 
1993). 
 
7. Provide clear navigation: Users should be able to move easily and efficiently 
through the interface. Navigation should be clear and intuitive (Shneiderman, 
1998). 
 
8. Make it visually appealing: The interface should be visually appealing and 
aesthetically pleasing. The design should be consistent with the users’ 
expectations and preferences (Nielsen, 1993).
